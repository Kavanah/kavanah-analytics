A stepped run keeps one probe user viewing dashboards for the whole run — its step-1 experience is the baseline (1.0×) everything else is compared against. Each simulated user fires all of a dashboard's chart queries every 2–5 seconds with almost no think time, so this models N users actively hitting dashboards simultaneously — N simulated users represent more than N real people. Pool identities see fewer dashboards than the probe (they are background load, that's expected). Unscoped identities (no workspace/org/team grant) can't see any dashboards at all and are left out by default so the user count means users actually loading dashboards; check "Include unscoped users" to add them back — their dashboards-list 403s are the scope gate working, not a broken run.

Import Capacity Test
Each selected row is a real import running fully in parallel with the others, re-importing an already-imported date range (never force-refetching). This models scheduled imports from different teams landing at the same moment — e.g. 100 workspaces averaging 5 sources with 25% scheduled together would mean ~25 overlapping imports. True parallelism is bounded by import locks: two selections whose lock groups conflict would silently serialize, so the server rejects them; same-source rows on different lock groups run concurrently , up to 20 per batch. Worst case auto-selects the N heaviest non-conflicting rows (echo > google_ads / GA4 / youtube > the rest), freshest data first — review the checked rows, then Run. light = Facebook skip-guards make the re-import nearly free. Runs alongside a load test or on its own.
